## Notes
The laptop (Apple M3 Max, APFS on the internal SSD), against the step 4 server before
open files were looked at every second. Output in `output-before.txt` beside this page.
Each root gets 20 appends, each through its own open and close, timed from the write to
the event that reports the new size, then a burst of 2 000 lines written a millisecond
apart through one handle, the way a training run writes its log.

| Measure | Before ([[RUN-20261024-p44p6z]]) | After ([[RUN-20261024-p68f0e]]) |
|---|---|---|
| append to event, watched root (notify), median / max | 264 / 266 ms | 266 / 267 ms |
| append to event, polled root, median / max | 1 496 / 1 500 ms | 495 / 786 ms |
| appends missed, of 20 per root | 0 | 0 |
| 2 000 lines through one open handle, events while writing (watched) | 2 in 2.8 s | 4 in 3.2 s |
| the same, polled root | 2 in 2.6 s | 4 in 2.7 s |

Appends that open and close the file arrive in 264 ms through FSEvents (the 250 ms
debounce and about 15 ms), every one of them. The burst did not: FSEvents reported the
file when it was opened and when it was closed and nothing in between, so a run's log
held open for hours would have been refreshed only by the 30 s safety check. Fixed by
looking at open files every second ([[RUN-20261024-p68f0e]]).


## Reproduce
Run `script` from the repo root in the project's dev shell at `commit`; it must produce the
same outputs. Note here what it cannot control.

`run.sh [directory]` builds a release binary and a scratch notebook whose two roots are in
that directory (default: a temporary one on the local disk), so it measures the
filesystem it is pointed at. Delays depend on load and on where the poll timer is when a
write lands. This run measured the code before the one-second look at open files: to
reproduce it, set the tick in `live.rs` back to 30 s when no root is polled.
