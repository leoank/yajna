## Notes
`===RESULT=== {"cases": 11, "fields": 88, "identical": 88, "reference_xorb_rebuilds_csv": true,
"reference_xorb_had_footer": false}`: every field of every case is the same through xet-core
1.8.0 and through `tools/yajna-xet` at b9d6117. The cases: empty, 1 byte, 8191 and 8192
random bytes, 128 KiB and 1 MiB + 3 of zeros, 300 MB of seeded random bytes and a copy with
1 byte inserted, 1 MiB deleted and 64 KiB overwritten, 16 MB of f32 (byte-grouped), 16 MB of
text (LZ4), and Hugging Face's 63.5 MB reference CSV. The fields: chunk boundaries and chunk
hashes (as digests), the file hash, each xorb's hash, size and serialized bytes with footer
(the per-upload nonce zeroed, so the compression chosen per chunk matches too), the shard
with lookup tables, and the shard as uploaded.

Found on the way, now in the crate and its tests (`tests/reference.rs`):
- The serialized xorb we write for the reference CSV is byte-identical to Hugging Face's
  reference xorb `eea25d6e…` once that is given its footer (both `2a2ba50d…`).
- Hugging Face's reference shards are written with a footer and no lookup tables (counts 0),
  as the CAS server stores them; xet-core's own cache writes the tables. Both are `Layout`s
  now, and all four reference shards serialize back byte for byte.
- A file's sha256 sits in the shard as four big-endian words (`Sha256::from_be_bytes`), so
  that its string form is the usual hex; a plain copy of the digest does not match.
- xet-core's client leaves a xorb's serialized size at 0 in the shards it writes (the spec
  says the size), uploads xorbs without footer, and the server adds one.
- The reference `.xorb` file ends with 4 stray bytes, `XETB`, after its 796 chunks: the
  start of a footer ident, cut off. Its chunks are complete; the harness strips them.
- The hex example in huggingface.co/docs/xet/api drops a `10`; the draft spec's is right.
- Grouping chunks into xorbs is the client's policy, not the format: both sides here use
  the same rule (close at 64 MiB or 8192 chunks). In the edited 300 MB copy only the
  first xorb survives the edit, though only a few chunks changed: deduplication has to
  work on chunks, not xorbs, which step 3 does and EXP-20261106-3t40bg measures.

The harness pins xet-core at `=1.8.0` and its `Cargo.lock`; the reference files are fetched
at dataset revision c4aa3a3f and checked by sha256. Not controlled: the network for the
first build and fetch. 58 s on rogue (M-series laptop), most of it building xet-core.
