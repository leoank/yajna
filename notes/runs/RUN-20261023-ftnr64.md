## Notes
The mirror cycle (ADR-0026) against the real Drive, at b4113ca plus the uncommitted
`mirror` build this run tested, in a scratch lab (namespace `yajna-mirror-check`).

Result: `{"exports_identical": true, "revision_export_identical": true}`; the guard
refused to publish over the outside edit; the pull's diff was

```diff
-A paragraph wrapped at ninety columns, with *emphasis*, **bold**, `inline code`, a link
+A paragraph wrapped at eighty columns, with *emphasis*, **bold**, `inline code`, a link
-- second item with *emphasis*
-  - nested item
+- second edited item with *emphasis*
+  - > nested item
```

and after a commit the page published again and a second pull found nothing.

- The design (architecture 5.8 as of b4113ca) assumed an unedited doc converts back to its
  source. A probe before this run showed it cannot: Drive's Markdown export drops code
  spans and blocks, writes lists as `> *` lines and headings in bold. But two exports of
  one doc were byte-identical and the published revision's export link gave the same
  bytes, so the pull compares export with export and carries the difference onto the
  source; ADR-0026 records the change.
- The edits came back word for word with the code span, link and citation around them
  untouched. `> nested item` is not an edit: the stand-in for a person re-uploads the
  doc's own HTML, and Google's re-import flattens nested lists. A person typing in the doc
  does not do that; [[EXP-20261023-ftnatx]] checks it with a real edit.
- An earlier probe found a spurious conflict: the published source was read through a
  `git` helper that trims output, which cut the trailing space of an empty `- [ ] ` item.
  It is now read untrimmed.
- Cleanup: the scratch root trashed, the scratch lab removed.
